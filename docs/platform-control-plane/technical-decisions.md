## 2. Module and persistence boundaries

## 3. Access foundation and identity compatibility

Engineering registers permissions with risk, scopes, actors, channels, dependencies, conflicts, workflow gating, and recent-auth metadata. Persist a catalog projection using only registered keys. Unknown keys cannot become executable permissions. Seed the 19 default business templates listed in master §5.2. Do not assign them globally merely because they exist.

Phase 1A adds persistence and lifecycle services only. Phase 1B adds `AuthorizationService` and an explicitly bounded `LegacyRoleCompatibilityAdapter`; later phases expand enforcement. Preserve the existing enum, JWT conversion, realm composites, patient/representative access, and endpoint gates until the replacement has parity tests.

Important migration constraint: `JwtRoleConverter` discards roles unknown to `ActorRole`, and `ActorContext.current()` rejects an authenticated subject with no recognized legacy role. Phase 1B must support database-authorized subjects independently of that legacy prerequisite. Adding new role names to Keycloak alone cannot deliver configurable access.

Legacy mappings:

| Current identity role | Intended mapping / constraint |
|---|---|
| DOCTOR | CONSULTANT; retain subject, practitioner ID, credential and assignment checks |
| COORDINATOR, OPERATIONS, FINANCE | Corresponding business templates with current resource scope |
| *_LEAD | Base template plus explicit supervisory scope; reporting visibility does not grant execution rights |
| CREDENTIALING_ADMIN | Explicit provider-onboarding/credential permissions matching migrated operations; never an unrestricted platform grant |
| SYSTEM_ADMIN | PLATFORM_ADMIN technical role; existing broad read/exception privileges stay confined to unmigrated legacy paths, never copied into the new template |
| AUDITOR | COMPLIANCE_AUDITOR with appropriate read scope; no mutation |
| PATIENT_IDENTITY_REVIEWER | Separate patient-identity permission bundle; never clinician credential-verification authority |
| PATIENT / PATIENT_REPRESENTATIVE | Existing ownership and patient_representatives delegation; no staff-template substitution |

Compatibility is not a universal fallback after a new-policy denial. Endpoint cutover must explicitly select the new enforcement path; absence/revocation of a new grant must not resurrect access through an old role. New SYSTEM_ADMIN semantics do not inherit the legacy clinical-access bypass.

## 4. Persistence design for Phase 1A

Planned migration: `V31__access_governance_foundation.sql` (recheck latest number immediately before creating it).

| Table | Key integrity and purpose |
|---|---|
| permission_definitions | Unique registered permission key; metadata persisted by registry synchronization |
| role_templates | UUID, stable template key, label, optional tenant scope, optimistic version |
| role_template_versions | Template FK, unique (template_id, version_number), lifecycle/effective dates, publisher, version column; published grants immutable |
| role_permission_grants | Version + permission FK + scope type; uniqueness for each grant/scope; channels and constraints validated against registry |
| role_assignments | Subject, pinned role-version FK, explicit scope type/target, effective/revoked timestamps, assigning actor, reason |
| resource_relationships | Typed source/target identifiers, organization scope when applicable, relationship type, effective dates/revocation, actor/reason |

Use explicit columns for security-relevant scope and identifiers; bounded serialized metadata only for validated catalog collections, not arbitrary executable policies. `PLATFORM` is explicit, exceptional and audited. Require scope identifiers for tenant/resource-sensitive assignments and deny unresolved organization facts until Phase 2 supplies the provider domain. Phase 1A does not create a fake provider entity or grant access based on an unverified UUID; Phase 2 adds provider FKs/backfill validation before provider enforcement is enabled.

Use UUIDs, timezone-aware timestamps, one ADD COLUMN per ALTER, portable constraints and indexes. Serialize mutation of one template by a row lock and optimistic version checks; enforce monotonically unique versions in the DB. Published versions cannot be edited; assignments pin a version. Reject duplicate overlapping effective assignments/relationships inside a serialized transaction, since partial active indexes are prohibited. Keep historical grants and revocations rather than deleting them. Add lifecycle, stale-write and concurrent-duplicate tests.

Reuse `audit_events` via a new access infrastructure repository. Phase 1A audit records can use entity ID plus reason; add an explicit organization/version/diff projection in a later additive migration where needed. Do not put clinical payloads or secret claims in audit. No live authorization cache.

## 10. Phase 1 implemented decisions (supersedes the Phase 0 plans above)

2026-09-13: current user authorization included full Phase 1 backend and Access Governance UI, so the earlier 1A-only/UI-deferred stopping boundary no longer applies. No Phase 2 provider/business execution has started.

- V31 adds the six originally planned tables plus `access_subjects`, `access_memberships`, `access_bootstrap`. Platform is the explicit reserved scope UUID `00000000-0000-0000-0000-000000000001`; it is not a fake provider organization. Provider membership is a pending foundation record, not trusted verification evidence.
- All role templates are governed centrally under platform ownership. Assignments carry the tenant boundary separately; custom actor types are distinct from template names. A subject can hold multiple tenant assignments. PLATFORM does not match provider tenants.
- Subject creation/mutations serialize on the bootstrap sentinel before subject/template locks. This deliberately conservative Phase 1 lock prevents absent-parent and cross-role SoD races without partial indexes. It is a throughput limitation for future optimization, not a tenant bypass.
- Only `access.*` permissions are executable. Other registered business capabilities are design-time foundation data until their authoritative owning resource resolvers exist. A UUID supplied by the browser never verifies an organization, activates a relationship, or supplies workflow authority.
- New `/api/v1/admin/access/**` security matcher authenticates identity; each service enforces the capability. AccessIdentity supports JWT subjects without recognized ActorRole. ActorContext/JwtRoleConverter/realm are unchanged. LegacyRoleCompatibilityAdapter provides migration suggestions only; it is never called as a fallback following DENY. Representative delegation remains solely in the existing patient model.
- Bootstrap is an opt-in deployment property `app.access.bootstrap-subject` (Spring environment form `APP_ACCESS_BOOTSTRAP_SUBJECT`). No default subject or API exists. It records one owner assignment and a completion marker transactionally. Restart cannot regrant after revocation; an existing authorized owner must grant a replacement. A second independent reviewer is required for publication and can be appointed through the effective-access assignment UI.
- Publication validates the full registry envelope and requires the publisher to hold every executable capability being delegated. Assignment applies the same check. Future permission grants remain non-executable; Phase 2 must add the appropriate business delegation envelope before enabling them.
- Successful audit writes share the mutation transaction; denied operations use a separate transaction so rejection rollback cannot erase the event. No clinical payloads or secret token claims are logged.
- Simulation can reference a saved draft version; evaluation includes current membership, registry constraints and combined assignment conflicts but evaluates the proposed grant instead of silently falling back to the user's existing grants. It never writes policy, assignments or relationships. Unresolved resources deny; other subjects have unknown recent authentication and therefore cannot appear recently authenticated by borrowing the reviewer's session.
- UI and API use the existing gateway client and OIDC flow. EN/AR UI is included now at the user's request; no React Flow/provider/designer work was introduced.

## 11. Final identity/authorization reconciliation

**Keycloak is authoritative for authentication and identity-session concerns. RehletShifaa is authoritative for dynamic business authorization, organization membership, roles, permissions, scopes and relationships.**

Keycloak owns OIDC Authorization Code + PKCE, passwords, MFA, login/session management, stable identity subjects and security account enable/disable/lifecycle. The browser remains a public S256 PKCE client. Realm/client roles retained on existing routes are coarse technical/legacy compatibility information, not configurable business policy. Never create resource-specific realm roles/groups (such as a role per doctor/manager/coordinator), synchronize dynamic DB roles into Keycloak, or fall back to ActorRole after a new-policy denial.

`access_subjects.active` is a local business-access suspension, not a second authentication account or a replacement for Keycloak's enabled state. Revoking an organization membership must not disable a person's identity in other organizations. Cached/display invitation status is not authorization evidence. Existing JWT session validation remains unchanged; account/session invalidation and application grant revocation are distinct operations.

### Identity provisioning boundary for Phase 2

`identity/IdentityProvisioningPort` exposes role-free `invite(name,email,locale)`, `resend(subject,locale)`, `setEnabled(subject,enabled)` and display `status(subject,storedStatus)`. Its `IdentityAccount` returns the stable external subject. The existing `KeycloakStaffIdentityService` implements this port, reusing the existing backend credentials, HTTP integration and invitation actions. No duplicate identity adapter or frontend Admin API exists. The four-argument invitation method remains exclusively for legacy staff/doctor realm-role compatibility; new provider business services inject the port and do not pass business roles to Keycloak.

The role-free invitation creates an enabled identity requiring email verification/password setup and sends Keycloak's action email. It performs no role lookup/mapping; realm defaults remain identity-provider configuration and confer no new business access. Invitation failure retains the existing best-effort identity cleanup. `status` may return stored display status if Keycloak is unavailable; it must never authorize membership or activation.

Phase 2 business orchestration must authorize the operator and resolve the organization first, call this backend port, store the returned subject with the existing person/profile identity, and persist organization membership, pinned role assignment, credential lifecycle and relationships in RehletShifaa. Keycloak and the application DB do not share an atomic transaction: implement durable retry/reconciliation for partial provisioning and DB failures, never link an existing identity solely from an unverified client email/subject, and activate business access only after required checks. Do not globally disable an identity merely to remove one organization membership. Provider orchestration is not implemented in this reconciliation.

### Security corrections and effective-access semantics

- The existing `JourneyService.verifyPractitioner` now rejects both approval and rejection of one's own credentials by resolving the profile's stored external subject, including for SYSTEM_ADMIN. The new evaluator's existing self-verification guard remains. Full provider credential lifecycle/activation remains Phase 2.
- Membership, assignment and published-version start timestamps normalize to DB microsecond precision, avoiding upward JDBC rounding that could transiently deny immediate grants/bootstrap. A fixed nanosecond regression reproduced the issue before correction. No migration or global timestamp behavior changed.
- Published assignments pin immutable versions. Removing a permission in v2 does not silently rewrite v1: revoke/replace v1 assignments or retire v1 to withdraw its permissions. The evaluator reads current DB state without an authorization cache; revocation/retirement denies subsequent decisions.
- Platform governance capabilities explicitly authorize central access administration/inspection. They do not imply provider/clinical access. `ASSIGNED_ORGANIZATIONS` uses an explicit assignment and active membership for each organization; PLATFORM is currently confined to the governance sentinel. Broader provider capabilities require reviewed resolver/envelope implementation in Phase 2, not a wildcard bypass.
- Effective-access responses explain assignment/version, permission, organization, scope, relationship type and allow/deny reason. Provider resource simulation remains unresolved/default-deny until its owning resolver exists. Denial reasons do not claim that a grant exists.

Final reconciliation accepts the Phase 1 foundation after the focused checks in test-status.md; it is not a live deployment certification. Provider, Journey and Coordinator routing execution remain unstarted.

## 12. Phase 2A provider foundation decisions

2026-09-14: Phase 2A introduces a real provider tenant boundary without changing legacy clinical/commercial execution.

- `provider_organizations` is the verified source for organization identity. Its UUID is distinct from every practitioner ID. DRAFT/ONBOARDING/SUSPENDED/OFFBOARDED are structural Phase 2A states; READINESS_REVIEW/ACTIVE remain unavailable until Phase 2B supplies computed readiness.
- `access_memberships` remains canonical membership and `role_assignments` remains canonical business-role assignment. `provider_membership_details` is a provider-specific extension holding practitioner/staff linkage and encrypted invitation display data, not a parallel authorization table.
- One subject can have multiple organization memberships and multiple pinned roles in one organization. Provider roles are published additive v2 versions; V31 records are not edited. New provider assignments pin v2 and do not rewrite existing assignments.
- `resource_relationships` remains the single relationship store. Provider orchestration is the trusted resolver that may create ACTIVE `MANAGES`, `ASSISTS` and `SUPERVISES` records only after checking both participants, clinician type, organization and membership; otherwise the relationship remains PENDING.
- Provider creation is the sole Phase 2A platform-scoped provider operation. Its creator receives organization-scoped Provider Operations access only for the created tenant. Reads and mutations require an active membership and an exact organization grant; a platform governance role or legacy realm role is not a provider wildcard.
- Phase 2A executes `provider.view/create/update/suspend/member.invite/member.deactivate/clinician.invite/practice_staff.manage/relationship.manage`. `provider.activate` and all credential, pricing, availability and clinical capabilities remain unavailable through the new evaluator.
- Consultants and Associate Doctors reuse `practitioner_profiles`; V32 only expands the existing type constraint. Practice Managers and Assistants are organization members and are not inserted into the internal `staff_members` directory unless an existing trusted staff record is being linked. Relationships, not role labels, carry managed/supervised/assisted clinician scope.
- V33 is a repeat-safe Java Flyway backfill because portable SQL cannot derive deterministic UUIDs consistently across H2 and PostgreSQL. It derives organization/assignment UUIDs from each practitioner UUID, preserves the practitioner row and all foreign keys, and creates DRAFT/PENDING_REVIEW/PENDING records. Review and activation are explicit Phase 2B work.
- Provider identity orchestration calls the role-free `IdentityProvisioningPort`. `provider_identity_operations` stores encrypted request data and durable REQUESTED/IDENTITY_CREATED/COMPLETED/FAILED state. The identity call occurs outside the membership transaction; a stable subject committed as IDENTITY_CREATED can be reconciled after a database failure. Existing identity reuse requires a stored practitioner/staff linkage, never an arbitrary client subject or email.
- Membership revocation changes only RehletShifaa membership, pinned assignments and provider relationships. It does not globally disable the Keycloak account, so other organizations remain unaffected.
- No frontend, Keycloak realm, pricing, scheduling, credential workflow, patient delegation, case assignment or Journey runtime contract changed in Phase 2A.

### 13.2 Identity and onboarding

- Preserve §11–§12: Keycloak owns identity, authentication and sessions; RehletShifaa owns roles, tenant membership, credentialing and readiness. Use `AccessIdentity`, not a recognized legacy realm-role prerequisite, on new APIs. Credential rejection, expiry, provider suspension or membership removal never globally disables a multi-organization identity.
- Extend the existing role-free provisioning port/adapter with a durable operation correlation ID. Commit the local operation before the external call and store that ID as a server-managed Keycloak user attribute during creation. Recovery must find exactly one matching server-created marker and persist its stable subject; email alone is not ownership proof. Zero/ambiguous matches remain unresolved and confer no access. A timeout/unknown result is reconciled before another create; do not blindly retry invitations or delete an ambiguously owned account. Keep business roles out of Keycloak.
- Lock and reread operation state before finalization, with unique subject/profile and operation constraints. An authorized retry of COMPLETED returns the stored result. Reconciliation reauthorizes the stored requested role's capability (`provider.clinician.invite`, `provider.practice_staff.manage` or `provider.member.invite`) against the stored organization, not only generic member invitation; a stale/revoked operator cannot finalize a grant. Resending an action email is separate from creating/linking membership.
- Add a clinician onboarding record per `(organization, practitioner)` rather than overloading global `practitioner_profiles.credentialing_status` or Keycloak account status. Use `INVITED → PROFILE_INCOMPLETE → DOCUMENTS_SUBMITTED → UNDER_VERIFICATION → VERIFIED → OPERATIONAL_SETUP → ACTIVE`, with `MORE_INFORMATION_REQUIRED`, `REJECTED`, `SUSPENDED`, `OFFBOARDED` exceptions. Profile completion/submission and review decisions drive transitions; arbitrary status PATCH is prohibited. Request-information permits a new submission; rejection permits a new revision for review; offboarding is terminal for that enrollment. Suspension requires an explicit authorized restoration and fresh readiness checks.
- Active business membership is allowed before clinical activation so clinicians can complete onboarding. No membership link, invite, activation, role assignment or wizard step sets clinical eligibility. Pending relationship activation must revalidate both stored identities, effective memberships, pinned roles and relationship dates. Readiness must recheck those facts even if a relationship row says ACTIVE.

### 13.3 Clinician meaning, policy and tenant ownership

- Consultant and Associate Doctor remain real `practitioner_profiles`; Assistant and Practice Manager are support memberships. An Assistant relationship grants no licensed status or final recommendation authority. An Associate requires independent credential verification plus an effective, same-tenant `SUPERVISES` relationship to an eligible Consultant; it never inherits the Consultant's final authority. Validate self-relationships by the target profile's subject, not by comparing a subject string with a practitioner UUID.
- Keep the stable practitioner person and existing credential IDs. Add provider credential dossier/link records, immutable credential submission revisions, evidence records and verification decisions. Each dossier is owned by one organization and practitioner; each decision names the exact revision/evidence IDs and policy version. Global legacy credential rows are compatibility/history, not cross-tenant authorization facts.
- No implicit sharing: membership in organizations A and B does not make A's evidence or decisions visible/effective in B. A new B dossier requires its own submission and review. Historical patient document references remain intact but do not become readable through provider APIs; a valid new provider evidence submission is required for adoption. Never fabricate a patient case or loosen the existing case-document access rules.
- Persist immutable, engineering-registered required-credential policy versions keyed by clinician type and jurisdiction. The initial fail-closed baseline requires identity, current professional license and qualification evidence for both clinician types, plus evidence supporting Consultant status for a Consultant; do not present this technical baseline as a jurisdiction's legal accreditation standard. Unknown/unconfigured jurisdiction or requirement yields `CREDENTIAL_POLICY_UNCONFIGURED`, never an empty passing policy. Policies explicitly state expiry applicability; a license needs a finite expiry, while a genuinely non-expiring credential type may omit it. Ordinary profile/provider updates cannot waive requirements. Policy setup is deployment-controlled in Phase 2B, not a new policy designer.
- Clinical credential eligibility requires **every** applicable mandatory requirement to have an independently verified, currently effective revision, no applicable suspension, and valid membership/clinician relationships. Profile labels, invitation completion, a single VERIFIED credential, and supervision alone never suffice.

### 13.4 Verifier authority and capability cutover

- Resolve `organization → enrollment → dossier → revision → evidence` from stored foreign keys for list, detail, upload, confirmation, review, download and activation. A mismatched parent returns no data. Require effective actor membership plus an exact tenant/resource grant on every operation. A platform governance assignment is not a wildcard across providers; an officer serving A/C receives explicit A/C access.
- Freeze submit/view and reviewer capabilities separately. Submit permits SELF or explicitly delegated organization/managed-clinician scope. Review, request-information, verify, reject and suspend require an explicitly assigned credential-review envelope; provider invitation/update authority, technical administration, patient identity review and role names confer none. `credential.verify` requires view/review dependencies and the existing 15-minute recent-auth rule; apply recent authentication to reject/suspend and provider/clinician activation too. Limit new execution to supported ADMIN_WEB/API and self-service CONSULTANT_WEB actions; do not enable future channels incidentally.
- All reviewer mutations (including entering review, request-information, reject, suspend and restoration) reject the clinician's own stored subject and the submitting actor for that revision. Multiple roles, organizations, impersonated client owner fields and SYSTEM_ADMIN provide no exemption. Self-service submission remains allowed. Reasons are mandatory for information requests, rejection, suspension and restoration; approval records the review basis and exact evidence.
- Before enabling capabilities, fix delegation in `RoleTemplateService`/`RoleAssignmentService`: retain independent central publication and immutable versions, but validate business grants against a registered delegable envelope rather than invoking a tenant permission on the PLATFORM sentinel. Explicit central access governance may assign the registered credential-verifier bundle to a resolved provider tenant after membership, scope, SoD and recent-auth validation; this administrative grant does not authorize the administrator to view evidence or verify. Provider-local managers can delegate only their permitted subordinate provider roles, never credential-verifier/platform authority. Custom grants outside the registered envelope fail closed.
- That central path must establish/review the officer's canonical effective `access_memberships` record in each assigned provider using a trusted existing subject, including an officer with no practitioner profile. Do not force officers through the provider-local clinician/staff invitation role list or create fake practitioners/internal staff. Central role publication controls the delegable definition; assignment supplies the concrete tenant and target scope, which publication alone cannot grant.
- Publish additive role versions and explicitly replace reviewed assignments. Audit existing pinned grants before turning catalog keys executable: dormant credential grants must not silently confer newly executable authority. No mass repinning or implicit bootstrap verifier; use the explicit central assignment path for the first independent officer. Synchronize the catalog projection and Effective Access resource resolvers in the same cutover.

## 18. Phase 4B domain action dispatch, Assignment Engine integration and authorization intersection — 2026-09-21

- **Dispatch replaces, not layers on, the prior slice's hardcoded open/close.** `JourneyActionHandler` (`open`/`complete`, typed `OpenContext`/`CompleteContext`) and `JourneyActionDispatcher` (deterministic action-key → handler map, built once from every registered bean; a startup-time collision on the same key is a configuration error, not a runtime coin-flip) are the single path `JourneyProjectionService` uses to open or complete any node, keyed by the node's registered `JourneyStageRegistry` action. A node whose action has no registered handler fails the whole `sync`/`completeWorkItem`/`completePatientAction` call closed — nothing opens, nothing advances — rather than falling back to generic behavior. The two handlers registered this session (`REQUEST_INFORMATION`, `PROVIDE_INFORMATION`) call exactly the domain methods the prior slice called directly; this re-homes already-approved behavior behind a real per-action contract, it is not new business logic, and the remaining nine registered actions are intentionally left unregistered (International Care v1 work).
- **`JourneyStageRegistry.sourceContract` remains documentation, never a reflective handler name** (per that class's own frozen comment) — handlers are hand-written Spring beans naming their action key explicitly, never derived from the registry string.
- **Assignment Engine integration reuses `retryQueued`, never `execute`, for the Journey-triggered path.** `execute`'s SHADOW-before-ACTIVATE adoption gate is a deliberate Phase 3 human safety control (frozen in §12 of this document); Journey never calls `execute` and therefore can never silently adopt LIVE routing for a case a human has not already reviewed. `CoordinatorRoutingPort.routeCoordinatorWork` only re-runs the already-idempotent, already-SYSTEM-triggered queue retry on a case already bound and LIVE, then reads the resulting owner — it changes nothing Phase 3 did not already decide, and resolves to no result (never an exception) for every other case state, so an infrastructure hiccup or an unbound/not-yet-adopted case degrades to the existing unassigned/queued WorkItem rather than failing Journey projection.
- **WorkItem owner is a hint, Case Owner is Phase 3's fact.** `RequestInformationActionHandler.open` sets the opened WorkItem's `owner_subject` from `routeCoordinatorWork`'s result but never writes `case_assignments`; only `AssignmentEngine.persist` (reached solely through `execute`, a human-authorized org-scoped action) can change Case Owner. This is the only way to satisfy "assignment of a WorkItem must not transfer Case Owner" without duplicating Phase 3's own eligibility/scoring/queue logic.
- **New capability `journey.work.execute`, family `journey_work` (not `journey`).** The existing `journey` family is hardcoded to `ActorType.GOVERNANCE` and `ScopeType.PLATFORM` only (`PermissionCatalog.register`) — correct for journey *administration* (view/edit/publish the graph) but wrong for case-level business *execution*, which needs `ActorType.COORDINATOR` and both `PLATFORM` (no resolved provider yet) and `ORGANIZATION` (a resolved provider) scope. A new family was added rather than overloading `journey`, mirroring how Phase 3 added the `assignment` family for the same reason. V42 registers the same key in the database projection and adds two role templates — `JOURNEY_WORK_PLATFORM` and `JOURNEY_WORK_ORGANIZATION` — with cutover records, matching the existing `journey.*`/`assignment.*` seeding pattern exactly.

- **`completeWorkItem` moved from creator-scoped to case-scoped binding lock** (`JourneyCaseBindingRepository.lockByCase`, new, unscoped by `created_by`) because the real business actor authorized by `journey.work.execute` is not necessarily the harness operator who admitted the verification case. `sync`, `completePatientAction` and `read` keep the creator-scoped `lock` — they remain on the admin/platform-governance verification-harness boundary this session did not redesign (opening work is a system event; no real patient authentication surface exists yet to intersect with).

An unauthorized caller therefore cannot use a duplicate-completion request to avoid re-proving authorization, and a stale/duplicate replay from an *authorized* caller is a safe no-op rather than a repeated domain call.

## 22. Bounded recovery-cycle support — 2026-09-22 (Claude Code)

**This supersedes §17's blanket cycle rejection for the specific case described here, not the general caution.** §17 said "these decisions do not relax Phase 4A cycle validation. Recovery-loop support... must be designed and tested against CaseTransitionPolicy before Phase 4B acceptance." This session does exactly that design/test work for the three approved loops — Consultant RETURN_TO_COORDINATOR, proposal REVISION_REQUESTED and proposal EXPIRED — and only for graphs that satisfy the bounded policy below. Cycles that do not satisfy it remain rejected exactly as before.

- **Where cycle rejection lived, and what changed.** `JourneyCompiler` never rejected cycles itself — it just serializes nodes/edges deterministically into plain BPMN `sequenceFlow`/`exclusiveGateway`/`userTask` elements, which natively support loops with zero code change. The rejection was entirely in `JourneyGraphValidator.validate`'s DFS `cycle()` check, which failed on *any* back-edge. That method is replaced by `validateCycles`/`walkCycles`/`validateBackEdge`, which still runs a DFS to find every back-edge (an edge whose target is an ancestor on the current path) but only rejects one that fails an explicit policy: **(1) not a self-loop** (`CYCLE_SELF_LOOP`); **(2) the back-edge's source must be a Decision stage** on a registered business fact, never an automatic/unconditional re-entry (`CYCLE_UNGATED`); **(3) the cycle (every node from the back-edge's target through its source) must contain at least one Staff or Patient action**, so a human business step is required before the loop can be traversed again — a Decision/System-only loop could spin without any external input (`CYCLE_NO_HUMAN_ACTION`). A cycle also needs an escape, but that was already guaranteed for free by the existing `NO_COMPLETION` backward-reachability check (every node, cycle members included, must already have a path to an End stage) — nothing new was needed there.
- **New Decision facts, not a scripting language.** `Fact` gained `CLINICAL_ACCEPTED` and `PROPOSAL_NEEDS_REWORK` (same mechanism as the existing `PROPOSAL_ACCEPTED`/`CONSULTANT_ACCEPTED`, a fixed enum of typed booleans, never an arbitrary expression). `RECORD_CLINICAL_DECISION`'s outcome and the patient's requested proposal decision are both caller-known *before* the completion call (the caller chose ACCEPT vs RETURN_TO_COORDINATOR, or ACCEPTED vs DECLINED vs REVISION_REQUESTED), so the fact is computed by the caller exactly like `PROPOSAL_ACCEPTED` already is — no handler-interface change was needed for these two loops.
- **The one genuinely discovered (not caller-declared) outcome: lazy proposal expiry.** `decideProposal`/`decideProposalPublic` check `validUntil` *before* looking at the requested decision at all, so a patient attempting any decision on an already-expired version is silently redirected to the expiry branch regardless of what they asked for. That branch persists the expiry (`proposal_versions`/`medical_cases` → EXPIRED) then throws `PROPOSAL_EXPIRED`, protected by that method's own `noRollbackFor=ApiException.class`. Calling it *through* `JourneyProjectionService` (class-level `@Transactional`, no such override) previously meant that exception would propagate out through that outer proxy boundary and mark the *shared* transaction rollback-only on the way out — silently undoing the expiry write the standalone (non-Journey) caller would have kept, a real, verified divergence (confirmed via Spring's per-boundary rollback-rule semantics: each `@Transactional` proxy the exception passes through applies its own rule against the same physical transaction). `ReviewProposalActionHandler.complete` now catches specifically `PROPOSAL_EXPIRED` and treats it as a real, successful completion outcome rather than letting it propagate — no new expiry policy, timer or state, just correctly adapting an outcome the unmodified domain method already produces. The caller still supplies `PROPOSAL_NEEDS_REWORK=true` proactively (the same `validUntil` check any caller can make itself), which is what actually routes the graph back to `prepare`.
- **Process-variable staleness across a loop is real and must be explicitly reset.** Flowable process variables persist across a loop unless overwritten. The `wait_consultant` WAIT (technical-decisions.md §21) reuses the same `CONSULTANT_ACCEPTED` variable on every pass; without resetting it, a second pass through the loop would find the *first* pass's leftover `true` and auto-advance (`advanceSatisfiedWaits`) without the new Consultant ever actually accepting. The Consultant-return handler resets it to `false` in the same `facts` map that routes the loop back to `assign`, at the exact completion call that decides to re-enter the loop. `JourneyHappyPathParityTest.consultantReturnToCoordinatorRecoveryLoopReopensAssignmentAndConverges` asserts the clinical WorkItem does *not* open until the fresh `signal(..., CONSULTANT_ACCEPTED=true)` — proving the reset actually took effect, not merely that the code compiles.
- **Projection identity: `journey_stage_projections` moved from one-row-per-(case,node) to one-row-per-visit.** V41's `UNIQUE(case_id,node_key)` assumed a node is visited at most once in a case's lifetime; a bounded loop breaks that assumption outright. V46 (a Java Flyway migration, like V33, because the unnamed V41 constraint gets a different non-deterministic auto-generated name in H2 versus PostgreSQL — verified empirically, H2 LEGACY mode produces an internal id like `CONSTRAINT_E08C3D`, not PostgreSQL's `<table>_<col>_key` convention, and JDBC `DatabaseMetaData.getIndexInfo` returns H2's separate backing-index name rather than the constraint name `DROP CONSTRAINT` needs — the ANSI `information_schema.table_constraints`/`key_column_usage` views are the actual portable source of truth) adds `engine_task_reference` and replaces that constraint with `UNIQUE(engine_task_reference)` — Flowable mints a fresh task id every time a userTask activity is (re)entered, so this is naturally correct for both a first-ever visit and a later legitimate revisit, while still rejecting duplicate delivery of the same live task. `sync()`'s idempotency check moved from "does any row exist for (case,node)" to "does a row exist for this exact task reference"; `completeWorkItem`/`completePatientAction`'s lookup moved from `lock(case,node)` to `lockLatest(case,node)` (most recent visit by creation time — unambiguous because Flowable only ever runs one live token through a given node at a time, so visits are strictly sequential), preserving the existing "replay of an already-completed node is a safe no-op" contract exactly, since the *latest* row is still whichever one is currently OPEN-or-was-just-COMPLETED. `completeAuthorizedPatientAction`'s patient path was already keyed by `case_task_id` (`lockByTask`), not node key, so it needed no change at all.
- **What was deliberately not touched.** `JourneyCompiler` (zero changes — loops are ordinary BPMN). `JourneyActionHandler`'s interface (zero changes — every loop's routing fact is caller-known except the one case above, handled inside the one handler that needs it). The frozen 11-action catalog (zero new actions). `JourneySimulator` gained a bounded `loopGuard` (graph node count ×3+50) purely as a defensive cap: it evaluates one *static* fact set for a whole dry run and cannot itself discover a loop's eventual exit (the real runtime differs because facts like `CONSULTANT_ACCEPTED` are explicitly reset and re-signaled between passes), so an admin choosing facts that satisfy a loop-back condition would otherwise spin forever; it now returns a distinct `LOOP_LIMIT_EXCEEDED` outcome instead of hanging. This does not affect publication: the one static fact set used for submission simply picks the straight-through, non-looping path, which is all a completed dry-run simulation ever needed to prove.

## 26. Phase 7B — controlled cutover policy — 2026-09-23 (Claude Code)

- **Configuration-controlled, not admin-managed.** Every existing Journey runtime switch is deployment configuration and no canonical doc specifies a business cutover console; a policy table + maker/checker API would be a new governance surface without a requirement. ## 25. Phase 7A — real Journey intake hook — 2026-09-23 (Claude Code)

- **The hook lives on `IntakeEvents.CaseSubmitted`, not inside `CaseService.submit()` itself.** `casemanagement` must stay free of a `journey` import (`ArchitectureRulesTest.businessModulesAreFreeOfCycles`); `journey` already imports `casemanagement` one-way (`JourneyCaseVerificationService`). A new `journey.application` bean (`JourneyProductionIntakeService`) listening for the event already published inside `submit()`'s own transaction gets the identical "one atomic operation" guarantee as an inline call, without adding a new dependency edge — the same reasoning `PatientAccountService.onCaseSubmitted` already relies on for a different feature on the same event.
- **Deliberately not a reuse of `JourneyCaseVerificationService`'s public API**, per this session's own explicit instruction not to blindly expose the verification/fixture service as production intake. That class (and `JourneyProjectionService`'s public methods) require an authenticated caller holding `journey.simulate` — the admin/platform-governance verification-harness boundary both classes' own Javadoc already documents. A system-triggered reaction to an already-accepted public intake command has no such caller. `JourneyProductionIntakeService` reuses the proven *lower-level* pieces instead (`JourneyDefinitionRepository`, `JourneyDeploymentRepository`, `JourneyCaseBindingRepository`, `JourneyRuntimePort`, and a new package-private `JourneyProjectionService.syncAsSystem`), never the `journey.simulate`-gated public surface.
- **`JourneyProjectionService.syncAsSystem` is package-private, not public.** It is a real, if narrow, relaxation of "every projection call is `journey.simulate`-gated" — the runtime reaching its first node after a genuine production admission is a system event with no human caller to authorize, exactly like `syncInternal`'s own existing "SYSTEM" subject convention for every other post-completion re-sync. Package-private visibility is the actual enforcement that it is reachable only from other `journey.application` classes, never from a controller — there is no annotation-based equivalent to rely on instead, and this repository's existing `journey.application`/`journey.api` package split already draws exactly this boundary for other classes.
- **Discovered during testing, not while reading the code: `JourneyProjectionService`'s constructor gate was wired to `case-verification-enabled` only.** The first focused test run failed closed with `Journey case verification is not enabled` even with the new intake flag on, because `syncAsSystem` shares `runtime()` with every other method. Fixed by taking both flags and enabling on either — this is a genuine, if small, architectural correction to already-accepted Phase 4B code, not new Phase 7A design; it widens, never narrows, who may reach the shared projection machinery, and the two pre-existing verification-harness suites were rerun clean to confirm no behavior changed for their existing callers.
- **New-case eligibility is "latest `PUBLISHED` version of the one canonical definition with a matching deployment," not a caller-supplied version id.** There is exactly one Journey definition by construction (`JourneyDefinitionRepository.create` refuses a second), so there is no multi-definition business mapping to invent. Requiring deployment-graph-hash match (not publication status alone) matches Phase 4A's own distinction that publication alone reports `NOT_DEPLOYED` (§16) — though in practice publishing with the runtime enabled already auto-deploys (`deployment.deployOnPublish`, called from inside `JourneyDefinitionService.publish`), so the "skip an undeployed newer publish" branch is defensive rather than the common path, and was code-reviewed rather than force-tested with a contrived fixture.
- **A Journey admission failure never blocks the underlying patient submission unless admission has already genuinely started.** Flag off, no engine bean, no eligible version — all a clean no-op; the case submission still succeeds on legacy authority, because an internal Journey configuration gap must never become a reason a real patient's intake request fails. Once the binding row is inserted, every subsequent failure (engine start, projection) is left to propagate uncaught and roll back the whole `submit()` transaction — a deliberate asymmetry, not an oversight, documented in the class's own Javadoc and proven by test (the case reverts fully to `DRAFT`, not left half-bound at `RECEIVED`).
- **New migration V47** widens V40's unnamed inline `CHECK (admission_mode = 'VERIFICATION')` to `IN ('VERIFICATION','PRODUCTION')` via the same portable-constraint-name-lookup technique V33/V46 already established (H2 and PostgreSQL auto-generate different names for an unnamed constraint). No other schema changed.
