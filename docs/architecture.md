# Architecture

## Components

- **Web:** Next.js App Router renders localized marketing and intake pages. Locale is part of every public URL, making canonical and alternate-language links deterministic.
- **API:** A Spring Boot modular monolith owns validation, state transitions, upload authorization, notification orchestration, and operational controls.
- **Database:** PostgreSQL stores cases and document metadata. Flyway is the only schema-change mechanism.
- **Object storage:** Medical files are private. The API issues short-lived presigned PUT URLs and verifies object metadata before a case can be submitted.
- **Email:** SMTP notifications contain the case reference and operational metadata only, not the patient's narrative or document contents.

## Domain and state

A medical case is created as `DRAFT` and may transition to `SUBMITTED`. A document starts as `PENDING`, becomes `UPLOADED` only after object verification, and may be `REJECTED`. The database enforces the core status and consent constraints.

The public case number is generated by PostgreSQL as `RS-YYYY-NNNNNN`. Internal relationships use UUIDs. Object keys are independently randomized.

## Trust boundaries

The browser is untrusted. MIME type, size, consent, case status, Turnstile token, and upload completion are verified server-side. Presigned URLs grant access to one random object key for a short period and do not grant bucket-list or read access.

The coordinator workflow is intentionally outside V1's public API. There is no patient-data listing or retrieval endpoint. A future authenticated staff portal should use a separate authorization boundary with MFA, least-privilege roles, immutable audit events, and session controls.

## Observability

Every request receives or propagates an `X-Correlation-ID`. Application logs are structured and avoid case narrative, contact details, filenames, and uploaded content. Only the liveness/readiness health endpoint is exposed by default.
