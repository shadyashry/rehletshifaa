# WhatsApp shared team-inbox / conversation-routing tools: assignment, collision prevention, integration, compliance, pricing, and build vs buy

Research date: 2026-10-10. Context: RehletShifaa is pre-launch, has one business WhatsApp number, has only a wa.me link, does not ingest inbound WhatsApp yet, and already has its own case-ownership engine (one owner coordinator per case, with continuity, preference, capacity/language scoring, a queue, and claim/reassign). Most sources below are vendor help centers (primary) or vendor/competitor blogs (secondary, potentially biased). Prices change often; every price is dated to when the source was read.

## Q1. How does assignment work in each tool, how do they prevent two agents replying, and how do queues and auto-close/reopen behave?

### Takeaway
Every vendor offers round-robin, and most offer a load-based mode ("least open" or capacity). True "sticky" routing, which sends a returning customer back to the agent they spoke to before, is a documented first-class option only in Infobip (sticky agent with a lookback window), Twilio (Known Agent Routing), and Zendesk (reopened tickets stay with the original assignee). Elsewhere you get it from a contact-owner field or a workflow. Collision prevention is mostly soft: assignment badges, typing/"is viewing" indicators, and visibility restrictions. I found no vendor with a hard "only the assignee may send" lock on WhatsApp. respond.io's "Restrict Contact Visibility" comes closest, because it hides other agents' contacts entirely.

### Cited Findings
**respond.io**
- Assignment can be manual or automated through Workflows. Only Owners and Managers can access the Workflows module, and each Workflow has exactly one trigger. — [respond.io Workflows overview](https://respond.io/help/workflows/workflows-overview); [Workflow Triggers](https://respond.io/help/workflows/workflow-triggers)
- There are two documented auto-assignment strategies. "Low-Cost" assigns users round-robin with "Only assign to online users" on. "High-Quality" assigns to the user with the fewest open contacts. The doc recommends routing to a team first when you have multiple teams, then assigning. — [respond.io Assignment Strategy](https://respond.io/help/convert-leads/assignment-strategy-automatic-contact-distribution-load-balancing)
- The Inbound Conversation Workflow pattern has three stages: data enrichment, routing to a team, then auto-assignment to an available agent. — [respond.io blog: routing workflows](https://respond.io/blog/chat-routing-contact-routing-workflows-module-respondio)
- In respond.io the assignee sits on the Contact, not on a ticket. `GET /v2/contact/{identifier}` returns an `assignee` field. — [respond.io API: Get a contact](https://developers.respond.io/docs/api/cbcfb23486778-get-a-contact)
- Replying to an unassigned contact automatically assigns it to the responder. — [respond.io Responding to Messages](https://respond.io/help/quick-start/responding-to-messages)
- "Restrict Contact Visibility" has two levels. The team level shows agents only contacts assigned to themselves or their team; the self level shows only contacts assigned to themselves, in the Mine and Collaborations inboxes. Unassigned contacts are hidden either way. — [respond.io User settings](https://respond.io/help/workspace-settings/users)
- Users have asked for a per-action "restrict ability to reply" permission. Restricted agents also cannot search for or message contacts outside their assignment, even to send templates. — [respond.io feature request: granular permissions](https://respond.canny.io/feature-request/p/user-settings-granularcustom-user-access-level-permissions)
- The Assignments report counts unassignments as assignments and records "Developer API" as an assignment source. — [respond.io Reports: Assignments](https://respond.io/help/dashboard-reporting/reports-assignments)

**Chatwoot**
- Auto-assignment is round-robin among available agents in an inbox and is on by default per inbox, under Collaborators > "Enable auto assignment". If no agent is available, the conversation stays "Unassigned". — [Chatwoot: round-robin assignment](https://www.chatwoot.com/hc/user-guide/articles/1677696868-assigning-conversations-in-a-round_robin-fashion)
- Collision detection works through typing indicators and assignment badges. Assigning a conversation to yourself shows the owner to the whole team. — [Chatwoot: Preventing Agent Collision](https://www.chatwoot.com/hc/user-guide/articles/1732243644-preventing-agent-collision); [Chatwoot Collision Detection feature page](https://www.chatwoot.com/features/collision-detection)
- Agent capacity limits are an Enterprise or paid-tier feature. — [eesel.ai Chatwoot pricing 2026](https://www.eesel.ai/blog/chatwoot-pricing) (secondary)
- Open GitHub bug #16134 (v4.18.0): with Assignment V2, new conversations are sometimes not auto-assigned. The reporter suspects the AssignmentJob runs before the creating transaction commits. — [chatwoot/chatwoot#16134](https://github.com/chatwoot/chatwoot/issues/16134)
- Open feature request #13516 asks for automatic reassignment when the assigned agent doesn't respond within X minutes, so this is not native. — [chatwoot/chatwoot#13516](https://github.com/chatwoot/chatwoot/issues/13516)

**Zendesk (Messaging / omnichannel routing)**
- Omnichannel routing routes by capacity, skills, priority, and agent status. Capacity is the maximum number of open tickets per channel. It is released when a ticket goes to Pending, On-hold, or Solved, or when a messaging conversation becomes inactive. — [Zendesk: Managing omnichannel routing configuration](https://support.zendesk.com/hc/en-us/articles/4828787357210-Managing-your-omnichannel-routing-configuration); [Zendesk: queues](https://support.zendesk.com/hc/en-us/articles/6712096584090-Understanding-how-omnichannel-routing-uses-queues-to-route-work-to-agents)
- By default, reopened tickets stay assigned to the original agent. An optional setting (Professional and above) reassigns reopened email and messaging tickets to another agent in the same group, but only if the current assignee's status is in an admin-defined list. If "Offline" isn't in the list, the ticket stays with the agent who went home. — [Zendesk announcement: reassign reopened tickets](https://support.zendesk.com/hc/en-us/articles/5952305148442-Announcing-the-ability-to-reassign-reopened-tickets-with-omnichannel-routing); [Macha: routing not working](https://www.getmacha.com/blog/zendesk-omnichannel-routing-not-working) (secondary)
- On Team and Growth plans, tickets can't re-enter a custom queue after being assigned. Professional and above can reassign through custom queues. — [Zendesk: Managing omnichannel routing configuration](https://support.zendesk.com/hc/en-us/articles/4828787357210-Managing-your-omnichannel-routing-configuration)
- Sunshine Conversations' "switchboard" controls which integration (a bot, Zendesk agent workspace, or a third-party system) is active on a conversation, via `passControl` and `releaseControl`. Closing a Zendesk ticket does not pass control back to the bot automatically. — [sunshine-conversations SwitchboardActionsApi](https://github.com/zendesk/sunshine-conversations-javascript/blob/master/docs/SwitchboardActionsApi.md); [Cognigy: Sunshine Conversations handovers](https://support.cognigy.com/hc/en-us/articles/360016224599-Sunshine-Conversations-Zendesk-Handovers)

**Twilio Flex / Conversations**
- TaskRouter "Known Agent Routing" (GA) targets a specific worker by SID or friendly name taken from a task attribute, for example `"known_worker_sid": "task.agent_sid"`. "Last agent routing" is a named use case. If the known agent is unavailable, the task falls back to other targets after a timeout. — [Twilio: Known Agent Routing](https://www.twilio.com/docs/taskrouter/workflow-configuration/known-agent-routing)
- Flex Conversations supports WhatsApp. To assign to a specific agent, Twilio says to use known agent routing, not a direct invite: a declined invite cancels the task but leaves the conversation active with no agent. — [Flex Conversations FAQ](https://www.twilio.com/docs/flex/developer/conversations/faq-and-troubleshooting); [Flex Conversations best practices](https://www.twilio.com/docs/flex/developer/conversations/best-practices)

**Infobip Conversations**
- Routes direct new conversations to queues. In auto-assign queues, an agent is chosen by availability, workload, and capacity. The "sticky agent" option assigns the conversation to the agent who last interacted with the customer, with a lookback of 30 days, 60 days, 1 year, or ever. If that agent is unavailable, standard auto-assignment applies. — [Infobip: Basic conversation settings](https://www.infobip.com/docs/conversations/conversations-setup/basic-settings); [Infobip: Queues and routing](https://www.infobip.com/docs/conversations-api/queues-and-routing)
- Via the API you can set a conversation to Unassigned and re-trigger routing, which is the usual pattern for bot-to-agent handoff. — [Infobip: Manage conversations over API](https://www.infobip.com/docs/conversations/conversations-over-api/manage-conversations-over-api)

**Intercom**
- Balanced assignment (Expert plan only) routes to the "present" teammate with the fewest assigned conversations, then the oldest last assignment. It respects both a personal limit and a team-inbox limit, and per-channel availability toggles. — [Intercom: Balanced assignment deep dive](https://www.intercom.com/help/en/articles/6553774-balanced-assignment-deep-dive); [Intercom: Workload management](https://www.intercom.com/help/en/articles/6560715-workload-management-explained)
- I found no WhatsApp-specific assignment controls in Intercom's docs. WhatsApp conversations use the general team-inbox rules. — [Octopods blog](https://blog.octopods.io/manage-whatsapp-messages-intercom/) (secondary)

**SleekFlow**
- Each conversation has exactly one "contact owner", the main person responsible for replying. Owners are set manually, by bulk edit, or by the Flow Builder "Assign to" node, which can target a specific user, a team, the queue order, or unassigned. Round-robin is the documented auto mode for new leads. — [SleekFlow: Assigning and collaborating](https://help.sleekflow.io/en_US/inbox/assigning-and-collaborating-on-conversations); [SleekFlow: Assign to node](https://help.sleekflow.io/advanced-flow-builder-actions/assign-to-action-node); [SleekFlow: round-robin template](https://help.sleekflow.io/en_US/advanced-flow-builder-templates/round-robin-assignment-for-new-leads-in-advanced-flow-builder)

**Callbell**
- There are three auto-assignment methods, set per team: round-robin; "smart" assignment, which balances by number of open conversations; and an online-only option. When "only available agents" is off, a closed chat that receives a new customer message can be reassigned if the original agent is unavailable. — [Callbell: How Automatic Assignment works](https://callbellsupport.zendesk.com/hc/en-us/articles/24886954423196-How-Automatic-Assignment-works); [Callbell: round robin](https://callbellsupport.zendesk.com/hc/en-us/articles/360002434018-Automatic-assignment-round-robin-in-Callbell)

**Trengo**
- Manual assignment works through "Assign to me" or by assigning to a user or team. Rules (condition → action) can auto-assign, for example sending a customer profile to a specific account manager, and can run on inbound, outbound, or assignment events. A round-robin rule is available. — [Trengo help: Assigning a conversation](https://help.trengo.com/article/assigning-a-conversation); [Trengo blog: 5 rules](https://trengo.com/blog/automate-tasks-in-your-inbox)
- The only reply restriction I found is role-based. A "light user" can assign conversations but cannot answer them. — [Trengo blog: WhatsApp multiple users](https://trengo.com/blog/whatsapp-business-multiple-users)

**Freshchat / Freshdesk**
- IntelliAssign routes by load (the agent with the most free bandwidth who has waited longest since their last assignment) or round-robin. Skill-based routing is Enterprise only. — [Freshworks: What is IntelliAssign](https://crmsupport.freshworks.com/support/solutions/articles/50000004357-what-is-conversation-routing-or-intelliassign-in-freshchat-); [Freshdesk Omniroute](https://support.freshdesk.com/support/solutions/articles/238979-ticket-assignments-with-freshdesk-omniroute-)

**Kommo**
- Kommo uses a "responsible user" model rather than a queue. Lead, Contact, and Buyer cards can each have their own responsible user, which can cause mismatches. Bots can change the responsible user. Native round-robin for chats wasn't confirmed; third-party widgets fill the gap. A permission level can restrict a user to items they are responsible for. — [ChatApp: responsible sync in Kommo](https://chatapp.online/en/help/responsible-sync-in-amocrm/); [Kommo: user permissions](https://www.kommo.com/support/account-settings/user-permissions/); [Kommo blog: chatbot conditions](https://www.kommo.com/blog/chatbot-conditions/)

**Bitrix24 Open Channels**
- Each channel has an agent queue with three modes: evenly, strictly in queue order, or to everybody (all agents see the chat and anyone can reply). Timed forwarding passes the chat to the next agent if there is no response. Unavailable agents are skipped. There is a per-agent cap on open conversations. — [Bitrix24: Configure agent queue](https://helpdesk.bitrix24.com/open/25782447/); [Bitrix24: Limit on open conversations](https://helpdesk.bitrix24.com/open/25830887/); [Bitrix24: Distributing inquiries](https://helpdesk.bitrix24.com/open/25890047/)

### Inferences
- (Inference) "One agent per customer" in these tools is enforced socially and through visibility, not transactionally. A tool's ownership model only matches RehletShifaa's "exactly one owner per case" if (a) agents are restricted to seeing their own assigned contacts and (b) assignment is driven from one authoritative source. Otherwise auto-assign rules in the tool can disagree with the backend's choice.
- (Inference) Most tools assign per contact or phone number (respond.io, SleekFlow, Kommo), not per case. A patient with two concurrent cases, or a family member messaging about someone else's case, does not map cleanly to a single contact assignee. This is a structural mismatch with a case-centric ownership engine.
- (Inference) The tools' native "sticky" routing (Infobip, Twilio, Zendesk, Callbell) duplicates RehletShifaa's continuity rule. If you buy, you would switch off the tool's auto-assignment and push assignment from the backend, so you pay for routing features you don't use.

### Gaps
- No primary-source detail found for WATI, Gupshup, or Kommo on round-robin vs load-based assignment or collision indicators.
- No primary-source confirmation of auto-close/reopen timers for respond.io, Trengo, WATI, SleekFlow, or Callbell (for example, whether a closed conversation reopens to the same assignee on a new inbound message). The respond.io "contact stays assigned" behavior is implied by the contact-level assignee but not explicitly documented in what I read.
- I did not verify Trengo's typing or "someone is viewing" collision indicators.

## Q2. Can assignment be set from an external system via API, do they push inbound-message webhooks, and can you look up contacts by phone and add custom fields such as a case number?

### Takeaway
Yes for most. respond.io, Chatwoot, Twilio, Infobip, Zendesk/Sunshine, Bitrix24, and Kommo all expose APIs to assign, unassign, and route, plus webhooks or events for inbound messages. respond.io supports phone-number lookup directly in the contact identifier. The main pitfall is echo loops: your own API writes come back as webhooks, and some payloads (Chatwoot) don't say who made the change. That makes two-way sync with an external ownership engine fiddly.

### Cited Findings
- respond.io Developer API (v2, base `api.respond.io/v2`) requires the Growth plan or above. The Conversations API can open or close conversations and assign or unassign users, human or AI. — [respond.io Developer API help](https://respond.io/help/integrations/developer-api); [respond.io API docs](https://developers.respond.io/)
- respond.io `GET /v2/contact/{identifier}` accepts a contact ID, phone number, or email as the identifier, and returns the `assignee`. — [respond.io API: Get a contact](https://developers.respond.io/docs/api/cbcfb23486778-get-a-contact)
- An AI agent assigned via the respond.io API doesn't reply on assignment; it replies after the next inbound message. — [respond.io Reports: Assignments](https://respond.io/help/dashboard-reporting/reports-assignments) (search-summary attribution; verify)
- respond.io offers Make and Zapier integrations, including a Zapier template that creates a contact, assigns an owner, and sends a welcome template. — [respond.io Make](https://respond.io/help/integrations/make); [Zapier template](https://zapier.com/automations/sales/crm-management/contact-management/create-contact-assign-owner-and-send-welcome-message)
- Chatwoot assignment API: `POST /api/v1/accounts/{account_id}/conversations/{conversation_id}/assignments` with `assignee_id` or `team_id`. If `assignee_id` is present, `team_id` is ignored. Conversation creation also accepts both. — [Chatwoot: Assign Conversation](https://developers.chatwoot.com/api-reference/conversation-assignments/assign-conversation); [Chatwoot: Create New Conversation](https://developers.chatwoot.com/api-reference/conversations/create-new-conversation)
- Chatwoot's `conversation_updated` webhook includes `changed_attributes`. Payloads have no `performed_by` field (open request #15914), so an integration can't tell its own API changes apart from automation or agent changes. — [Chatwoot changelog](https://www.chatwoot.com/changelog); [chatwoot/chatwoot#15914](https://github.com/chatwoot/chatwoot/issues/15914)
- A reported Chatwoot bug: auto-assignment fired `conversation_updated` but not `conversation_status_changed` on a pending→open transition. — [chatwoot/chatwoot#9277](https://github.com/chatwoot/chatwoot/issues/9277)
- Twilio: all attributes in the Interactions API `routing` object are copied onto the TaskRouter task. If you run your own orchestration, Twilio says to create tasks via the TaskRouter API rather than the Send-to-Flex widget or Interactions API. — [Twilio Interactions resource](https://www.twilio.com/docs/flex/developer/conversations/interactions-api/interactions); [Flex Conversations FAQ](https://www.twilio.com/docs/flex/developer/conversations/faq-and-troubleshooting)
- Infobip exposes queue and routing management and conversation assignment over its API. — [Infobip: Manage queues and routing over API](https://www.infobip.com/docs/conversations/conversations-over-api/manage-queues-and-routing-over-api)
- Zendesk Sunshine Conversations lets an external system take control of a conversation via the switchboard `passControl` endpoint (`POST /v2/apps/{appId}/conversations/{conversationId}/passControl`). — [SwitchboardActionsApi](https://github.com/zendesk/sunshine-conversations-ruby/blob/master/docs/SwitchboardActionsApi.md)
- Freshchat groups carry a routing type (INTELLIASSIGN or DISABLED), and the Freshchat API exposes conversations and assignment. — [Freshchat API](https://developers.freshchat.com/api/)
- Bitrix24 Open Channels (`imopenlines`) has REST methods and events, including connectors for custom channels. — [Bitrix24 Open Channels API](https://apidocs.bitrix24.com/api-reference/imopenlines/index.html)
- Kommo has a Chats API for registering custom chat channels. — [Kommo: Register a chat channel](https://developers.kommo.com/reference/register-channel)
- SleekFlow syncs contact owners with Salesforce, which shows owner sync from an external system of record is a supported pattern. — [SleekFlow Salesforce integration](https://sleekflow.io/en-us/blog/salesforce-integration)

### Inferences
- (Inference) Buy-and-sync means a one-way authority rule. RehletShifaa's backend decides the owner and calls the tool's assign API; the tool's auto-assign is disabled; inbound webhooks feed the backend so it can link messages to cases. You then need idempotent sync, echo suppression (ignore webhook events caused by your own writes, for example by comparing them to the last value you wrote), and reconciliation jobs, because there is no actor field (Chatwoot) and no transactional guarantee.
- (Inference) A custom contact field holding a case number works for a single active case per phone. It breaks for multiple cases per phone, which is the same mismatch noted in Q1.
- (Inference) Because the WhatsApp number can be connected to only one Cloud API app/BSP at a time, buying a tool means the tool owns the webhook. Your backend gets messages second-hand through the vendor's webhook, adding a hop and a vendor-specific payload format.

### Gaps
- I did not confirm custom-field write endpoints for respond.io, Chatwoot (custom attributes), or Trengo from primary API docs in this pass. I believe they exist (Chatwoot "custom attributes" and respond.io "custom fields"), but I have no citation.
- I did not verify Trengo, WATI, Gupshup, Callbell, or Intercom assignment or webhook API endpoints from primary docs.
- I did not confirm whether a WhatsApp number can be shared between a BSP-hosted inbox and a direct Cloud API webhook. This is likely not possible except through "coexistence" with the Business App; verify with Meta docs.

## Q3. What is the HIPAA/GDPR/data-residency posture, BAA availability, hosting regions, encryption, and audit logs, how suitable is each for medical data, and is there Egypt/MENA presence and Arabic/RTL support?

### Takeaway
The weak link is WhatsApp itself. Meta does not sign BAAs, and its business terms disclaim fitness for heightened-confidentiality sectors such as healthcare. So no inbox vendor's BAA makes the WhatsApp leg HIPAA-covered. Zendesk and Twilio sign BAAs for specific products, but Zendesk tells HIPAA customers not to enable third-party channels unless they take responsibility for PHI. respond.io claims GDPR compliance and ISO 27001 on AWS but publishes no region or BAA. Self-hosted Chatwoot is the only option that keeps message data in RehletShifaa's own infrastructure (Egypt/EU of your choosing). Arabic RTL UIs are confirmed for respond.io and Chatwoot.

### Cited Findings
- WhatsApp/Meta does not sign BAAs. Meta's business terms make no representation that the services meet heightened-confidentiality requirements such as healthcare. — [Paubox: Is WhatsApp HIPAA compliant (2025)](https://www.paubox.com/blog/whatsapp-hipaa-compliant); [HIPAA Vault](https://www.hipaavault.com/resources/is-whatsapp-hipaa-compliant/) (secondary; Meta terms quoted through these)
- Zendesk HIPAA-enabled accounts require the Advanced Security or Advanced Compliance add-on, specific security configurations, and a signed BAA. Zendesk's configuration requirements say not to enable third-party channel integrations unless the subscriber ensures no PHI is in those messages or holds its own BAA with the messaging platform. — [Zendesk Trust Center](https://www.zendesk.com/trust-center/); [Zendesk: Security configuration requirements for HIPAA/HDS accounts](https://support.zendesk.com/hc/en-us/articles/4408828395802-Security-Configuration-Requirements-for-HIPAA-or-HDS-Enabled-Accounts-on-Zendesk)
- Zendesk's Data Center Location add-on is free on Suite Professional and above, but it lists Support, Chat, Guide, Gather, Explore, Talk, and WFM. Messaging and Sunshine Conversations are not listed. — [Zendesk: About the Data Center Location add-on](https://support.zendesk.com/hc/en-us/articles/4408838409754-About-the-Data-Center-Location-add-on); [Zendesk Regional Data Hosting Policy](https://support.zendesk.com/hc/en-us/articles/4408883599130-Regional-Data-Hosting-Policy)
- Twilio signs BAAs for its listed HIPAA-eligible products; secondary sources say this requires Security or Enterprise Edition. I found no confirmation that WhatsApp is on the eligible list. — [Twilio changelog: Voice/SIP/SMS HIPAA eligible](https://www.twilio.com/en-us/changelog/programmable-voice--sip--and-sms-are-now-hipaa-eligible); [Twilio HIPAA-eligible products PDF](https://twilio-cms-prod.s3.amazonaws.com/documents/HIPAA-eligible-products-and-services.pdf); [Paubox: Is Twilio HIPAA compliant (2026)](https://www.paubox.com/blog/twilio-hipaa-compliant)
- respond.io says it is GDPR compliant, runs on AWS, holds ISO 27001, and offers DPAs on request (privacy@respond.io). Its security page gives no hosting region. — [respond.io Security](https://respond.io/security); [respond.io DPA](https://respond.io/data-processing-agreement); [respond.io Privacy Policy](https://respond.io/privacy-policy)
- respond.io's pricing page lists 2FA on all plans and phone/email masking, SSO, and multiple workspaces on Advanced and Enterprise. It does not mention HIPAA or a BAA. — [respond.io Pricing](https://respond.io/pricing) (read 2026-10-10)
- respond.io offers an Arabic UI with full RTL layout and Arabic platform emails. Arabic is in beta on the mobile Inbox app. — [respond.io changelog: Arabic available](https://respond.canny.io/changelog/arabic-language-is-now-available-in-respondio); [respond.io mobile language changelog](https://respond.canny.io/changelog/choose-your-preferred-language-on-respondio-inbox-mobile-app)
- Chatwoot's UI switches to RTL automatically for Arabic and Hebrew, and its Help Center and widget support RTL. — [Chatwoot changelog](https://www.chatwoot.com/changelog); [chatwoot/chatwoot#686 RTL support](https://github.com/chatwoot/chatwoot/issues/686)
- Chatwoot Enterprise (cloud) adds SSO/SAML, audit logs, and agent capacity management. — [eesel.ai Chatwoot pricing 2026](https://www.eesel.ai/blog/chatwoot-pricing) (secondary)
- One listicle claims Infobip is "HIPAA compliant out of the box". This is weak evidence and unverified. — [Sobot: 10 best WhatsApp API platforms 2026](https://www.sobot.io/blog/10-best-whatsapp-business-api-platforms-customer-service-2026/)
- A competitor-authored comparison claims WATI's panel languages are limited to English, Chinese, Spanish, and Portuguese, which would mean no Arabic. — [go4whatsup GCC comparison](https://www.go4whatsup.com/compare/best-whatsapp-crm-for-gcc/) (competitor source; treat with caution)

### Inferences
- (Inference) For an Egypt-based platform serving international patients, the relevant regimes are Egypt's Personal Data Protection Law (Law 151/2020) and GDPR for EU patients, more than HIPAA, unless US covered entities are involved. A vendor holding message transcripts becomes a processor of health data (a GDPR Art. 9 special category), which needs a DPA and transfer basis. Self-hosting (Chatwoot or in-house) removes the third-party inbox processor but not Meta.
- (Inference) Whatever the inbox choice, WhatsApp should be treated as a contact and notification channel, with clinical documents kept in the platform (MinIO/S3 with access control) rather than circulating as WhatsApp media in a vendor's storage. That argues for ingesting media into RehletShifaa's own store.

### Gaps
- No primary source found for BAA or HIPAA status at respond.io, WATI, Trengo, SleekFlow, Callbell, Kommo, Gupshup, Intercom, Freshworks (one secondary claim says Enterprise tier), or Bitrix24.
- No source found on any vendor's physical Egypt or MENA data hosting. I also have no confirmation of where the Meta Cloud API stores message data at rest.
- Arabic UI support for Trengo, SleekFlow, Callbell, Kommo, Freshchat, Intercom, and Zendesk agent UI was not verified in this pass.

## Q4. What do these tools cost (2025–2026)?

### Takeaway
SMB WhatsApp inboxes cost roughly $80–$350 per month for 3–10 seats before Meta fees. respond.io adds Monthly-Active-Contact (MAC) billing, and its API and Workflows (needed for external assignment) start at Growth: $159/month annual, 10 users. Chatwoot is the cheapest to license (MIT self-host free; paid self-host $19–$99/agent/month). Third-party price reports conflict, so treat non-vendor figures as estimates.

### Cited Findings
- **respond.io** (vendor page, read 2026-10-10, page dated 2026-10-09): Starter is $79/mo annual or $99 monthly, 5 users. Growth is $159/mo annual or $199 monthly, 10 users. Advanced is $279/mo annual or $349 monthly. Enterprise is custom. The extra-user mapping is inferred: about $12, $20, and $24 per user. MACs start at 1,000, with overage of $12 per 100 MACs on Growth and $15 per 100 on Advanced. Developer API and Workflows are Growth and above. "WhatsApp fees are not included in any respond.io subscription." A markup is not stated. — [respond.io Pricing](https://respond.io/pricing)

## Q6. What are the architecture patterns and pitfalls of building ingestion and an in-platform reply UI on the WhatsApp Cloud API?

### Takeaway
The core pieces are well understood, but production details are easy to get wrong. Webhooks are at-least-once and unordered, so you need signature verification, fast acknowledgement, a durable queue, idempotent upserts keyed on message and status IDs, and monotonic status transitions. Media URLs expire after 5 minutes, so media must be downloaded promptly into your own store (and should be virus-scanned). Every outbound send needs a 24-hour-window check with template fallback. Presence, off-shift handover, and SLA timers are entirely yours to build. RehletShifaa already has most of these as its routing engine and queue.

### Cited Findings
- **Delivery semantics**: Meta webhooks are at-least-once, so duplicates are normal. Deduplicate on `messages[].id` (inbound) and `statuses[].id` (status). Ordering isn't guaranteed, so sequence by the payload `timestamp`. — [Hookdeck: WhatsApp webhooks guide](https://hookdeck.com/webhooks/platforms/guide-to-whatsapp-webhooks-features-and-best-practices)
- **Retries**: a non-200 or timeout is retried with exponential backoff for up to 7 days, then dropped, with no DLQ or native replay. This is attributed to Meta by third parties and not confirmed against Meta docs. — [Hookdeck](https://hookdeck.com/webhooks/platforms/guide-to-whatsapp-webhooks-features-and-best-practices); [richautomate: webhook reliability 2026](https://richautomate.in/blog/whatsapp-webhook-reliability-engineering-guide-2026)
- **Ack deadline**: sources conflict. One says 3 seconds, another under 5 seconds, and Hookdeck says 5–10 seconds depending on BSP ("Meta recommends under 10s"). Design for the strictest. — [richautomate](https://richautomate.in/blog/whatsapp-webhook-reliability-engineering-guide-2026); [hellohub: Cloud API webhook guide](https://hellohub.ai/en/blog/whatsapp-cloud-api-webhook-guide); [Hookdeck](https://hookdeck.com/webhooks/platforms/guide-to-whatsapp-webhooks-features-and-best-practices)
- **Capacity**: Meta reportedly recommends webhook servers handle 3x outgoing plus 1x incoming traffic, because each outbound message produces up to three status callbacks (sent, delivered, read). Payloads can be up to 3 MB. — [Hookdeck](https://hookdeck.com/webhooks/platforms/guide-to-whatsapp-webhooks-features-and-best-practices)
- **Security**: verify `X-Hub-Signature-256` (HMAC-SHA256 of the raw body with the app secret, `sha256=` prefix) using a constant-time compare. Subscription uses a GET with `hub.mode`, `hub.verify_token`, and `hub.challenge`. — [Hookdeck](https://hookdeck.com/webhooks/platforms/guide-to-whatsapp-webhooks-features-and-best-practices)
- **Idempotency**: use a DB unique constraint plus an atomic upsert, because check-then-insert races. Never move status backwards (a late `sent` must not overwrite `read`). The webhook layer should verify, store the raw event, return 200, and do business actions in idempotent queue consumers. — [richautomate](https://richautomate.in/blog/whatsapp-webhook-reliability-engineering-guide-2026)
- **Production gotchas** listed in one Cloud API console case study: idempotent webhook processing, typing-indicator sequencing, coexistence echo deduplication, and encrypted data exchange. — [CodePrism: PrismWA case study](https://codeprismtechnologies.com/case-studies/prismwa-whatsapp-cloud-api-console)
- **Media**: media URLs expire after 5 minutes (re-query the media ID for a new URL), and webhook media IDs expire after 7 days. Downloads need the access token. — [Meta for Developers: Media](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-phone-numbers/media); [Medium: download Cloud API media to S3](https://medium.com/@shreyas.sreedhar/downloading-media-using-whatsapps-cloud-api-webhooks-and-uploading-it-to-aws-s3-bucket-via-nodejs-07c5cbae896f)
- **24-hour window**: non-template messages are allowed only within 24 hours of the user's last message, and each inbound message restarts the window. After it closes, an approved template is required. A common bug is retrying failed sends without checking the window. — [Meta: Cloud API Get Started](https://developers.facebook.com/documentation/business-messaging/whatsapp/get-started); [smsmode: 24-hour window and templates](https://www.smsmode.com/en/whatsapp-business-api-customer-care-window-ou-templates-comment-les-utiliser/); [Ominiflow](https://ominiflow.com/blog/whatsapp-24-hour-session-window)
- **Reference fault-tolerant architecture** for support platforms (vendor blog). — [WasenderAPI: fault-tolerant WhatsApp infrastructure](https://wasenderapi.com/blog/how-to-architect-a-fault-tolerant-whatsapp-api-infrastructure-for-customer-support-platforms)
- **Routing design** for WhatsApp lead routing and workflows. — [Ramaaya: WhatsApp lead routing systems](https://www.ramaaya.com/insights/whatsapp-business-api-automation-workflows)
- **Even mature open-source inboxes hit routing race conditions** (Chatwoot's Assignment V2 job running before the transaction commits) and lack native unanswered-reassignment SLA. — [chatwoot/chatwoot#16134](https://github.com/chatwoot/chatwoot/issues/16134); [chatwoot/chatwoot#13516](https://github.com/chatwoot/chatwoot/issues/13516)
- **Self-hosting Chatwoot** needs three values from Meta (WABA ID, Phone Number ID, permanent or system-user token). Template sending is supported only on WhatsApp Cloud inboxes. — [Chatwoot: WhatsApp manual setup](https://www.chatwoot.com/hc/user-guide/articles/1756799850-how-to-setup-a-whats_app-channel-manual-flow); [Chatwoot: WhatsApp templates](https://www.chatwoot.com/hc/user-guide/articles/1754940076-whatsapp-templates)

### Inferences (build vs buy, marked as inference)
- (Inference) **The case for building (option b)**: RehletShifaa already owns the hard, domain-specific part (one owner per case, continuity, capacity and language scoring, queue, claim/reassign). An inbox tool would duplicate it and assign per contact rather than per case. The missing pieces are commodity plumbing: a webhook receiver, an idempotent message store, a media pipeline into the existing MinIO/S3 with a virus scan (for example ClamAV), a send service with window and template logic, and a reply panel on the case page. A hard "only the case owner can send" check can be enforced server-side, which no surveyed tool offers natively. Message data stays in-platform, which helps with PDPL/GDPR health-data handling.
- (Inference) **The case for buying (option a)**: fastest time to launch; mobile agent apps, presence, templates UI, and broadcast are included; no on-call burden for webhook infrastructure. It works best if you accept contact-level assignment and push the backend's owner via API (respond.io Growth+, Chatwoot, Infobip, Twilio). Costs include two sources of truth, echo-loop and reconciliation logic, per-seat and MAC fees, and PHI in a third-party processor without a published region or BAA (respond.io).
- (Inference) **A hybrid worth naming**: self-hosted Chatwoot as the agent UI, with RehletShifaa as the assignment authority via the Chatwoot assignments API and Chatwoot auto-assignment disabled. This keeps data in your own infrastructure at low licence cost, but you then run and patch a second Rails app and still need echo suppression, since there is no `performed_by`.
- (Inference) For a pre-launch, single-number, small-team operation, a minimal in-house slice is tractable and aligns with existing architecture: inbound ingestion linked to the case by phone or patient identity, owner-only reply, a window indicator with template fallback, media into MinIO, and status ticks. Defer presence and SLA timers to the existing routing engine's capacity and handover rules. The highest-risk items to get right first are idempotency, monotonic status, the media expiry race, and the window check.
